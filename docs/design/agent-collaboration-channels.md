# Agent 协作通道：Hook 适配范围与省资源方案

> 状态：部分已实施（2026-09-07）——B0–B5 通道全部落地（状态来源、Copilot Hook、Pi/OMP 与 OpenCode 进程内直连、界面与 `observed` 兜底、冒烟脚本）；此后按用户方案重构了协作模型：C6 主动投递整段移除、交接改走信箱、技能与 Hook 解耦、按名字寻址、新增 `interrupt`，见 [协作指南](../guides/agent-collaboration.md)。§1 仍描述设计时的基线 `b3516e5d`。本文回答三个问题——Pi / Oh My Pi / GitHub Copilot 是否需要 Hook 适配；Agent 之间的交流方式是否已定、是否经 Hook；能否用更省资源的通道完成消息、状态 / 上下文采集与交接。现状以基线 `b3516e5d`（2026-09-06）的源码为准，三种 CLI 的接入点以其公开文档为准（§2 附来源）；不改 [Agent 协作](../guides/agent-collaboration.md)与[架构](../guides/architecture.md)已描述的既有行为。
> 范围：`crates/hook`、`apps/runtime/src/{hook,collab,handoff,context_usage.rs,context_estimate.rs,agent.rs}`、`packages/shared/src/{agents,hook-events}.ts`、设置页「Hook 与 Skills」、`proto/armadra/v1/agent.proto` 的注释与枚举。不含自动化调度、用量看板。
> 2026-09-20：下文所有 `.rs` / `.proto` 路径与 `cargo` 命令都是写这份文档那天（Rust Runtime + Go Host 分进程时代）的落点；此后 Runtime 与 Host 已合并重写为 TS core（`apps/desktop/src/core/`），这些路径不再存在，仅作实施批次的历史记录保留，通道设计与验收标准本身仍按本文为准，当前落点以源码与[协作指南](../guides/agent-collaboration.md)为准。

## 0. 结论

| #   | 问题                                      | 结论                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Pi / OMP / Copilot 是否需要 Hook 适配     | **协作本身不需要**：`post / inbox / ack`、`context list / terminal`、`handoff-read` 今天已经不依赖任何 provider hook（§1.4）。**需要一个状态来源**的是三件事：节点状态（working / waiting / done）、交接与 `send` 的空闲门、单会话上下文占用。三种 CLI 都有可接入点，代价都是「一个安装器 + 一个归一化器」的量级：Copilot 走命令 Hook（与 Claude 同构），Pi / OMP 走 TS 扩展（与 OpenCode 插件同构，且能直接给出精确上下文占用）。 |
| 2   | Agent 之间的交流方式是否已定、是否经 Hook | **已定，且不经 Hook 事件**。默认通道是 `armadra.mailbox.v1`：SQLite `agent_mailbox` 表上的拉取信箱，`armadra-hook` 二进制只是它的传输客户端（经 `hook.sock`），provider 的 hooks 配置不参与。经 Hook 状态的只有主动投递（`send / reply / notify`）和交接通知的**空闲门**，它们是显式选择而非默认。                                                                                                                                 |
| 3   | 能否更省资源                              | 现状已经没有对 CLI 的常驻轮询；主要开销是每个 Hook 事件 fork 一次 `armadra-hook`（§1.2）。推荐：**不新增协议**，把 `hook.sock` 上的同一 HTTP 协议作为唯一入口；对有进程内扩展能力的 CLI（Pi / OMP / OpenCode）改为**扩展进程内直连 socket**，去掉 fork；MCP、文件系统信箱、新的长连接协议都不推荐（§3.1）；PTY 侧观测只作展示级兜底，不作投递门（§3.4）。                                                                          |

| 层          | 凭据                                                            | 判定                                                                                                            | 代码                                              |

### 2.2 结论与代价

| CLI      | 是否做适配 | 形式                                                                                                          | 代价                                                                                                                                                              | 得到                                                                                                                       |
| -------- | ---------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Copilot  | 做         | 命令 Hook：安装器写 `~/.copilot/hooks/armadra.json`，`exec` 指向 `armadra-hook`，`args: ["copilot"]`          | 一个安装器（与 `install/claude.rs` 同构，识别规则仍是「命令含 `armadra-hook`」）+ 一个归一化器；**不订阅 `preToolUse`**（fail-closed 会让缺失二进制变成拒绝工具） | 节点状态、交接投递、`send`；转录路径（`agentStop.transcriptPath`）；上下文占用视 `events.jsonl` 字段而定                   |
| Pi       | 做         | TS 扩展：安装器写 `~/.pi/agent/extensions/armadra-status.ts`（生成、带 revision，与 OpenCode 插件同一套规则） | 一个安装器 + 一个归一化器 + 一份扩展模板（Pi / OMP 共用）                                                                                                         | 节点状态、交接投递、`send`；**精确上下文占用**（`getContextUsage`，`source: provider_hook`）；转录路径（`getSessionFile`） |
| Oh My Pi | 做         | 同 Pi，路径 `~/.omp/agent/extensions/`                                                                        | 复用 Pi 模板；差异在安装路径与事件别名                                                                                                                            | 同 Pi                                                                                                                      |

不做适配的替代——只保留「按需协作」——是可接受的产品状态，但交接投递和状态显示对这三种 CLI 永远缺席；本文认为三者代价都在一个批次内，值得做。

### 2.3 本机核实结果（B1 / B2，2026-09-06）

§2.1 标了「本机核实」的项目在实施批次里逐条验证，结论如下。凡是核实为「没有」的能力位一律不开——这是 §6 的规则，不是这一轮的临时决定。

| 项目                        | 批次 | 结论                                                                                                                                                                                                                                                                                                                                                                                    |
| --------------------------- | ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Copilot `events.jsonl` 字段 | B1   | **无逐轮 token 字段**。占用数字（`currentTokens` / `systemTokens` / `conversationTokens` / `toolDefinitionsTokens`）只出现在 `session.compaction_start` 与 `session.shutdown`，两者都晚于「描述一个活着的会话」所需的时刻；旧版本的 `assistant.message.outputTokens` 是回复自身长度，1.0.83 已不写。因此 Copilot 的 `contextUsage` **不开**，`estimate_events_jsonl` 写好但不接能力位。 |
| Copilot 载荷形状            | B1   | **载荷不带事件名**：`sessionStart` 收到的是 `{sessionId, timestamp, cwd, source, initialPrompt}`，事件名只存在于 hooks 文件的键上。归一化按字段组合判形状，模糊对（都带 `stopReason`）按「更窄的先匹配」排序；载荷里若真出现 `hook_event_name` 仍以它为准。camelCase 与 PascalCase 别名都会触发，两种拼写各调一次。                                                                     |

### 3.4 PTY 侧观测（兜底，展示级）

对没有任何状态来源的终端（自定义 CLI、用户拒绝安装适配），Runtime 已经知道两件事：最近一次输入围栏的序号（`observation.rs` 的 `input_revision`）和之后有没有输出。据此可以给出 `observed: active / quiet`（例如输入后 2 s 内无新输出即 `quiet`）。规则：

1. 只用于节点头部的弱提示与自动命名触发，标识为 `stateSource: observed`。
2. **不得**写入 `agent_status.state`，**不得**满足 `handoff_idle` 或 `send` 的空闲门，**不得**触发投递队列 `flush_for`。
3. 不解析提示符、不识别 OSC；只用已有的输出泵计数，不新增读取。
